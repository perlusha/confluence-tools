# Сборка матрицы согласования из дерева страниц

Скрипт: `Build-ApprovalMatrix.ps1`

Обходит дерево Confluence на любую глубину, находит страницы с верхней таблицей
согласования (строки «NN. Согласующий N») и собирает из них плоскую матрицу
на указанной странице.

---

## Запуск

```powershell
$env:CONFLUENCE_URL = 'https://confluence.example.com'
$env:CONFLUENCE_PERSONAL_TOKEN = '<PAT>'

# план (ничего не меняет)
.\Build-ApprovalMatrix.ps1 -Root 467853802 -Target 123456789

# запись
.\Build-ApprovalMatrix.ps1 -Root 467853802 -Target 123456789 -Apply
```

Параметры:

| параметр | смысл |
|---|---|
| `-Root` | корневая страница дерева (ID или URL) |
| `-Target` | страница, куда записать матрицу |
| `-Apply` | создать пилюли и записать; без него — только план |
| `-MaxPages N` | ограничить число страниц (для проверки) |
| `-Force` | создать пилюли заново, не переиспользуя существующие |
| `-Insecure` | не проверять TLS-сертификат |

Токен берётся из `CONFLUENCE_PERSONAL_TOKEN` / `CONFLUENCE_PAT`, база — из
`CONFLUENCE_URL` / `CONFLUENCE_BASE` (как в остальных скриптах).

---

## Что получается

Из дерева берутся **только те страницы, где есть таблица с согласующими** — то есть
строка вида `NN. Согласующий N` (даже если имена и статусы не заполнены). Таблица
«Лист согласования» (роли + ФИ + Да/Нет) не используется.

Матрица:

- **строки** — документы (по одной на страницу), в порядке обхода дерева; название
  раздела — **ссылка на страницу-источник**;
- **столбцы** — согласующие: объединение `userkey` по всему дереву, отсортированное
  **по частоте** (кто встречается чаще — левее); в шапке — ссылки на пользователей
  (`ri:user`), поэтому матрицу потом можно синхронизировать закладкой;
- **ячейки** — живые пилюли `status-handy` со статусом согласующего; где согласующего
  нет — прочерк `-`.

Шапка: `A1:B3` — «Наименование раздела»; `C1` — «Согласующие»; под ней **одна пустая
полоса**; затем строка со ссылками на согласующих. Данные — со строки 4.

---

## Как это работает

1. **Обход дерева** — `GET /rest/api/content/{id}/child/page` рекурсивно, все уровни.
2. **Разбор страницы** — из storage берутся строки `NN. Согласующий N`, из них
   `ri:userkey` и `id` пилюли.
3. **Живой статус** — по каждому macroid:
   `GET /rest/handy-macros/2.0/status-macro/{macroid}?contentId={pageId}`.
   Берётся текущий статус, а не снимок из тела страницы.
4. **Создание пилюль** — по одной на заполненную ячейку:
   `POST /rest/handy-macros/2.0/status-macro` с `contentId` и `statusId`.
   Приложение возвращает новый macroid, он и вставляется в ячейку. Без этого шага
   пилюля не отрендерится — макрос ссылается на запись в реестре приложения.
5. **Запись страницы** — `PUT /rest/api/content/{id}` с собранной таблицей.

Создание пилюль идёт **до** записи страницы: сначала приложение регистрирует все
статусы, потом они попадают в разметку.

---

## Важно знать

- **Повторный запуск безопасен.** Существующие пилюли переиспользуются по паре
  (название документа, согласующий) — новые создаются только для появившихся ячеек.
  `-Force` заставляет создать всё заново (старые останутся «сиротами» в базе приложения —
  API удаления статус-макроса нет).
- **Страница получается широкой** — число столбцов равно числу разных согласующих
  по дереву (в проверке на ФТТ — 55). Узкие столбцы (1.4%) заданы в разметке.
- **Согласующий попадает в столбцы только если у него есть пилюля.** Строка
  «Согласующий N» с именем, но без статуса, столбца не создаёт — статус не прочитать.
- **Строки-блоки** («ABC-ОПР-01 Концептуальный дизайн блока…») тоже попадают в матрицу
  строкой из прочерков, если у них есть таблица согласования.
- **Долго.** На 119 страницах и 477 заполненных ячеек прогон занимает около минуты
  (плюс обращения к API приложения).

## Проверено

На дереве `467853802` («Этап 4.1 Концептуальный дизайн», 207 страниц):

| | |
|---|---|
| страниц с таблицей согласования | 119 |
| столбцов-согласующих | 55 |
| заполненных ячеек | 477 |
| создано пилюль | 477 |
| отрендерилось (`data-status` в `body.view`) | 477 |

Результат — страница 123456789, версия v4.
